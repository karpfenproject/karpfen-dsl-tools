# 2.3 KStates

A KStates text is a state machine. It has states, which carry actions that read and write the model, and transitions,
which lead from state to state when their conditions hold. A file has the extension `.kstates` and holds one state
machine. The grammar of the language is `src/main/antlr/io/karpfen/dsl/grammar/kstates/Kstates.g4` in the
karpfen-dsl-tools repository.

The exact behaviour of each construct at run time is in
[3.1 Execution semantics](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/reference/3.1-execution-semantics.md).

The examples of this section run on the lamp metamodel of [2 Modeling languages](2-modeling-languages.md), in which the
room also holds a list of spare bulbs:

```kmeta
type "Bulb" "A light bulb that burns with watts, up to maxWatts" {
    prop("maxWatts", "number")
    prop("watts", "number")
    prop("lit", "boolean")
}
type "Switch" "A wall switch" {
    prop("position", "string")
    prop("presses", list("string"))
}
type "Lamp" "A lamp with a bulb, wired to a switch" {
    prop("mode", "string")
    has("bulb", "Bulb")
    knows("control", "Switch")
}
type "Room" "The room the lamp stands in, with spare bulbs" {
    has("lamp", "Lamp")
    has("switch", "Switch")
    has("spares", list("Bulb"))
}
```

## 2.3.1 The state machine

A text starts with `STATEMACHINE ATTACHED TO "Type"`, where `Type` is a type of the domain metamodel. The braces after
it hold the block `STATES`, then the block `TRANSITIONS`, then the block `MACROS`, in this order. `STATES` and
`TRANSITIONS` are required, `TRANSITIONS` may be empty, and `MACROS` may be left out.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "off" { }
    }
    TRANSITIONS { }
}
```

The state machine runs on one object of the type it is attached to. Every path of the state machine starts at this
object, unless it starts with one of the names that [2.3.3.2 Paths](#2332-paths) lists. Which object of the model it is,
a run decides by the key of the object.

A text may instead start with `STATEMACHINE "name" ATTACHABLE TO "Type", ...`. Such an attachable state machine is a
definition with a name and one or more types. A run does not attach it by a key. The runtime builds an instance of it
for each object that a `behaves after` of its type, an `ATTACH` clause or an `EXCHANGE` names it for, see [2.3.11 State
machine management and lifecycle](#2311-state-machine-management-and-lifecycle). The name is required, and each type is
listed once.

```kstates
STATEMACHINE "glowing" ATTACHABLE TO "Bulb" {
    STATES {
        INITIAL STATE "dark" { }
    }
    TRANSITIONS { }
}
```

The attachable form belongs to the optional feature `attachment`, see [2.3.10 Optional
features](#2310-optional-features).

## 2.3.2 States

`STATE "name" { ... }` defines a state. No two states of a state machine have the same name, whatever their depth.
Transitions refer to states by their names.

### 2.3.2.1 Nesting

A state may hold inner states, which are written inside its braces after everything else of the state. While an inner
state is active, the states around it are active too. A transition that starts at an outer state also applies while the
state machine is in one of its inner states.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "off" { }
        STATE "on" {
            STATE "full" { }
            STATE "dimmed" { }
        }
    }
    TRANSITIONS {
        TRANSITION "off" -> "full" {
            CONDITION { EVENT("switch", "press") }
        }
        TRANSITION "full" -> "dimmed" {
            CONDITION { EVENT("switch", "dim") }
        }
        TRANSITION "on" -> "off" {
            CONDITION { EVENT("switch", "press") }
        }
    }
}
```

A press switches the lamp off from `full` and from `dimmed`, since the transition from `on` applies in both. A
transition into a state with inner states enters the state itself and none of its inner states.

### 2.3.2.2 The initial state

The keyword `INITIAL` in front of `STATE` marks the state the state machine starts in. Exactly one state of the whole
state machine is marked. It may be an inner state: the state machine then starts in it and in the states around it.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        STATE "on" {
            INITIAL STATE "full" { }
        }
    }
    TRANSITIONS { }
}
```

### 2.3.2.3 Parts of a state

A state holds these parts, each of them optional, in this order:

1. `BREAKPOINT { ... }`, see [2.3.9 Breakpoints](#239-breakpoints)
2. `TICK LIMIT { ... }`, see [2.3.8 Tick limits](#238-tick-limits)
3. `ENTRY { ... }`, see [2.3.3.1 Entry and do blocks](#2331-entry-and-do-blocks)
4. `DO { ... }`
5. the inner states

In front of `STATE` stand `INITIAL` and then a history, `SHALLOW HISTORY` or `DEEP HISTORY`, see
[2.3.7 Histories](#237-histories), each of them optional.

## 2.3.3 Actions

### 2.3.3.1 Entry and do blocks

`ENTRY { ... }` holds the actions a state runs once when the state machine enters it. `DO { ... }` holds the actions it
runs in every tick in which it is the innermost active state. A block holds action rules, `IF IN SCOPE` blocks and
`WITH` blocks, which run in the order they are written.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "off" {
            ENTRY {
                SET("mode", "off")
                SET("bulb->watts", "0")
            }
        }
        STATE "warming up" {
            ENTRY {
                SET("mode", "on")
            }
            DO {
                SET("bulb->watts", EVAL { return min($(bulb->watts) + 10, $(bulb->maxWatts)) })
            }
        }
    }
    TRANSITIONS {
        TRANSITION "off" -> "warming up" {
            CONDITION { EVENT("switch", "press") }
        }
    }
}
```

While the lamp is in `warming up`, every tick gives the bulb 10 W more, up to its maximum. A state has no block for
leaving it.

### 2.3.3.2 Paths

A path names a property or a relation. It is a string of keys joined by `->`, and it starts at the object the state
machine runs on: `"mode"` is the mode of the lamp, `"bulb->watts"` the watts of its bulb and `"control->position"` the
position of the switch the lamp knows. A path follows `has` and `knows` relations alike. A path that goes on after a
list relation goes on from the first object of the list. Spaces around a key are ignored, so a key that is used in paths
should not contain `->`.

A path starts somewhere else if its first key is one of these names:

| First key | Where the path starts |
|---|---|
| `event` | At the payload of the event in scope, see [2.3.5 Events](#235-events). |
| The name of a `WITH` block around it | At the result of its macro, see [2.3.3.7 WITH blocks](#2337-with-blocks). |
| A parameter of the macro, in the code of a macro | At the value of the parameter, see [2.3.6 Macros](#236-macros). |

### 2.3.3.3 Action rules

An action rule names an operation and its operands in parentheses. The first operand is always a string.

| Rule | What it does |
|---|---|
| `SET("path", value)` | Writes the value into a property that is not a list. |
| `APPEND("path", value)` | Adds the value at the end of a list property. |
| `SETLIST("path", value)` | Replaces a list property with the list that its `EVAL` or `MACRO` returns. |
| `DROPLIST("path")` | Empties a list property. |
| `SETOBJ("source", "relation", target)` | Sets the relation of the object at `source`, which holds one object, to the target. |
| `APPENDOBJ("source", "relation", target)` | Adds the target to the list relation of the object at `source`. |
| `DROPOBJ("path")` | Removes the object at the path from the model, with every reference to it. |
| `EVENT("domain", name)` | Raises an event of the name in the domain, without payload. |
| `EXCHANGE("path", name)` | Ends the state machine of the object at the path and attaches an instance of the attachable state machine of the name. |

The source of `SETOBJ` and `APPENDOBJ` is a path to an object; `"self"` and `""` name the object the state machine runs
on. The target of a `has` relation must be a new object, which a `MACRO` or an `EVAL` builds. The target of a `knows`
relation must be an object of the model: a path to it, or a macro that returns `reference("Type")`. Every operation
except `EVENT` may also be written in lower case, such as `set`.

A `SETOBJ` or `APPENDOBJ` on a `has` relation may end with `ATTACH name`, after its parentheses. The clause names the
attachable state machine that the object the rule creates gets. `EXCHANGE("path", name)` replaces the state machine of
an object of the model. In both, the name is a value: a string is the name itself, not a path, and an `EVAL` or a
`MACRO` returns it as a string. `ATTACH` may also be written `attach`. Both belong to the optional feature `attachment`;
[2.3.11 State machine management and lifecycle](#2311-state-machine-management-and-lifecycle) shows them at work.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "off" {
            ENTRY {
                SET("mode", "off")
                DROPLIST("control->presses")
            }
        }
        STATE "on" {
            ENTRY {
                SET("mode", "on")
                APPEND("control->presses", "on")
                EVENT("lamp", "switched on")
            }
        }
        STATE "reset" {
            ENTRY {
                SETLIST("control->presses", EVAL { return ["reset"] })
            }
        }
    }
    TRANSITIONS {
        TRANSITION "off" -> "on" {
            CONDITION { EVENT("switch", "press") }
        }
        TRANSITION "on" -> "reset" {
            CONDITION { EVENT("switch", "press") }
        }
        TRANSITION "reset" -> "off" { }
    }
}
```

A state machine attached to the room changes relations. It wires the lamp to the switch, adds a new spare bulb and
removes the bulb from the lamp:

```kstates
STATEMACHINE ATTACHED TO "Room" {
    STATES {
        INITIAL STATE "rewiring" {
            ENTRY {
                SETOBJ("lamp", "control", "switch")
                APPENDOBJ("self", "spares", MACRO("new bulb", "lamp->bulb->watts"))
                DROPOBJ("lamp->bulb")
            }
        }
    }
    TRANSITIONS { }
    MACROS {
        MACRO "new bulb" {
            TAKES("watts", "number")
            RETURNS("Bulb")
            DEFINITION {
                EVAL { return {"watts": $(watts)} }
            }
        }
    }
}
```

### 2.3.3.4 Values

The last operand of a rule, its value, has one of three forms.

| Form | Example | Value |
|---|---|---|
| A string | `"40"` | For `SET` and `APPEND`, the text read as the type of the property: a number, `true` or `false`, or any text. For `SETOBJ` and `APPENDOBJ`, a path to an object. For `EVENT`, the name of the event. |
| `EVAL { code }` | `EVAL { return $(bulb->maxWatts) / 2 }` | What the code returns, see [2.3.3.5 EVAL code](#2335-eval-code). |
| `MACRO("name", "path", ...)` | `MACRO("half", "bulb->maxWatts")` | What the macro returns, see [2.3.6 Macros](#236-macros). |

A number or a boolean is written as a string too, as in `SET("bulb->watts", "0")`. Without the quotes it is a syntax
error.

### 2.3.3.5 EVAL code

`EVAL { ... }` holds code that the runtime runs as Python. It can be the value of a rule, a clause of a condition or the
definition of a macro. The code returns its result with `return`.

The runtime prepares the code before it runs it. Each `$(path)` becomes the current value at the path, so
`$(bulb->watts) + 10` adds 10 to the watts the bulb has at this moment. Each `@name(arguments)` becomes a call of the
macro `name`, which takes one argument per `TAKES` of the macro:

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "dimmed" {
            ENTRY {
                SET("bulb->watts", EVAL {
                    full = $(bulb->maxWatts)
                    return @half(full)
                })
            }
        }
    }
    TRANSITIONS { }
    MACROS {
        MACRO "half" {
            TAKES("watts", "number")
            RETURNS("number")
            DEFINITION {
                EVAL { return $(watts) / 2 }
            }
        }
    }
}
```

The code may run over several lines. The library reads it as KStates text up to the closing brace, so the braces in the
code must pair up. Braces and `//` inside string literals of the code do not count. Outside string literals, `//` starts
a KStates comment that runs to the end of the line: `return a // b` loses `// b`, and a closing brace after it on the
same line. Write `int(a / b)` for the integer division and `#` for a Python comment.

### 2.3.3.6 IF IN SCOPE blocks

`IF IN SCOPE("path", ...) { ... }` runs the actions inside only if every path it names can be read at this moment. A
path that starts with `event` can be read if an event is in scope and its payload has that field. Any other path can be
read if it leads to a value from the object the state machine runs on. A state that the state machine enters with and
without an event can read the payload this way:

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "off" { }
        STATE "on" {
            ENTRY {
                SET("bulb->watts", EVAL { return $(bulb->maxWatts) })
                IF IN SCOPE("event->bright") {
                    SET("bulb->lit", EVAL { return $(event->bright) })
                }
            }
        }
    }
    TRANSITIONS {
        TRANSITION "off" -> "on" {
            CONDITION { EVENT("switch", "dim") }
        }
        TRANSITION "on" -> "off" {
            CONDITION { EVENT("switch", "press") }
        }
    }
}
```

Several paths are separated by commas, and the block runs only if all of them can be read. Blocks may be nested.

### 2.3.3.7 WITH blocks

`WITH MACRO("name", ...) AS "binding" { ... }` runs the macro once and gives its result the name `binding` for the
actions inside the block. The code of an `EVAL` inside reads the result as `$(binding)`, or a value of an object result
as `$(binding->key)`, and the arguments of a macro call inside may start with the name too. `with` and `as` may also be
written in lower case.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "on" {
            ENTRY {
                WITH MACRO("brightest", "bulb->maxWatts") AS "best" {
                    SET("bulb->watts", EVAL { return $(best) })
                    SET("bulb->lit", EVAL { return $(best) > 0 })
                }
            }
        }
    }
    TRANSITIONS { }
    MACROS {
        MACRO "brightest" {
            TAKES("limit", "number")
            RETURNS("number")
            DEFINITION {
                EVAL { return $(limit) }
            }
        }
    }
}
```

Both rules see the same result, even when the macro returns another value each time it runs.

## 2.3.4 Transitions

`TRANSITION "from" -> "to" { ... }` leads from one state to another. The braces may hold a `BREAKPOINT` block and then a
`CONDITION` block. A transition without a `CONDITION` block fires whenever the runtime tries it. A transition may lead
from a state to the state itself.

### 2.3.4.1 Conditions

`CONDITION { ... }` holds one clause or more. The transition fires only if all clauses hold. The runtime checks them
from top to bottom and stops at the first one that fails.

| Clause | Holds when |
|---|---|
| `EVENT("domain", "name")` | An event of this name waits in this domain, see [2.3.5 Events](#235-events). |
| `VALUE("path")` | The boolean property at the path is true, or the string property at the path is `true` in any case. `VALUE("true")` always holds and `VALUE("false")` never. |
| `EVAL { code }` | The code returns true. |

A condition has at most one `EVENT` clause. Write it first: the clauses after it can read the payload of the event.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "on" {
            STATE "dimmer" {
                ENTRY {
                    SET("bulb->watts", EVAL { return $(bulb->watts) - 10 })
                }
            }
        }
    }
    TRANSITIONS {
        TRANSITION "on" -> "dimmer" {
            CONDITION {
                EVENT("switch", "dim")
                EVAL { return not $(event->bright) }
                EVAL { return $(bulb->watts) - 10 >= 0 }
            }
        }
    }
}
```

The lamp gets dimmer on a `dim` event whose payload has `bright` set to false, unless the bulb is already at 0 W.

### 2.3.4.2 Order and NOT LOOPING

The runtime tries the transitions of the innermost active state first and those of the states around it after. It tries
the transitions of one state in the order they are written, and the first one whose condition holds fires. The order of
the `TRANSITIONS` block is therefore a priority.

`NOT LOOPING` after the target keeps a transition from firing twice in a row. When the runtime skips it for this reason,
it tries the next transition. It has an effect only on a `TRANSITION`, not on a split or a join.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "on" {
            DO {
                SET("bulb->watts", EVAL { return $(bulb->watts) - 1 })
            }
        }
        STATE "check" { }
    }
    TRANSITIONS {
        TRANSITION "on" -> "on" NOT LOOPING {
            CONDITION { VALUE("bulb->lit") }
        }
        TRANSITION "on" -> "check" { }
        TRANSITION "check" -> "on" { }
    }
}
```

While the bulb is lit, the state machine enters `on` again, but not twice in a row: in between it takes the transition
to `check`.

### 2.3.4.3 Splits and joins

A split leads from one state into two or more states that are active side by side, each in a branch of its own. A join
leads from such states back into one state.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "off" { }
        STATE "bulb test" { }
        STATE "switch test" { }
        STATE "tested" { }
    }
    TRANSITIONS {
        SPLIT "off" -> "bulb test", "switch test" {
            CONDITION { EVENT("service", "test") }
        }
        JOIN "bulb test", "switch test" -> "tested" { }
    }
}
```

`SPLIT "from" -> "a", "b", ...` names two targets or more, each once. `JOIN "a", "b", ... -> "to"` names two sources or
more, each once. Both take `NOT LOOPING`, a `BREAKPOINT` block and a `CONDITION` block like a `TRANSITION`. The runtime
takes a split only while no branches are active, and a join only when each of its sources is active in a branch of its
own; a join comes before the transitions of the branches. See
[3.1 Execution semantics](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/reference/3.1-execution-semantics.md)
for the branches.

## 2.3.5 Events

An event has a domain and a name, and it may carry a payload. The domain and the name are any strings: in the lamp,
presses arrive in the domain `switch` and the smash in the domain `service`. Events come from the `EVENT` actions of
state machines and from outside the runtime, see
[3.4 HTTP API](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/reference/3.4-http-api.md),
[3.5 WebSocket](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/reference/3.5-websocket.md) and
[4.7 Bridges](https://github.com/karpfenproject/karpfen-IDE/blob/main/docs/reference/4.7-bridges.md).

The clause `EVENT("domain", "name")` holds when an event of this domain and name waits. The event that fires the
transition is then in scope: the clauses after the `EVENT` clause, the state the transition leads to and the states
inside it read its payload with paths that start with `event`, such as `event->bright` or `$(event->bright)`. The event
stays in scope while that state is active.

The payload of an event has the type of the same name in the event metamodel, see
[2.1.7 Event definitions](2.1-kmeta.md#217-event-definitions). The event `dim` of the lamp carries `bright`:

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "on" { }
        STATE "brighter" {
            ENTRY {
                SET("bulb->watts", EVAL { return $(bulb->watts) + 10 })
            }
        }
    }
    TRANSITIONS {
        TRANSITION "on" -> "brighter" {
            CONDITION {
                EVENT("switch", "dim")
                VALUE("event->bright")
            }
        }
        TRANSITION "brighter" -> "on" { }
    }
}
```

## 2.3.6 Macros

A macro is a named piece of code with typed parameters. The block `MACROS` at the end of a state machine holds the
macros, each written as `MACRO "name" { ... }` with these parts in this order:

1. `TAKES("parameter", type)` for each parameter, none or more
2. `RETURNS(type)`, exactly once
3. `DEFINITION { EVAL { code } }`, exactly once

| Type | Meaning |
|---|---|
| `"string"`, `"number"`, `"boolean"` | A primitive value. |
| `"Type"` | An object of a type of the domain metamodel or of the event metamodel. As a result, a new object. |
| `list("type")` | A list of values of the type. |
| `reference("Type")` | Only in `RETURNS`: an object that is already part of the model. |

The code reads a parameter as `$(parameter)`, and a value of an object parameter as `$(parameter->key)`. A macro that
returns a new object returns a Python dictionary of its values, such as `{"watts": 40}`, see the example of
[2.3.3.3 Action rules](#2333-action-rules).

`MACRO("name", "path", ...)` calls a macro as the value of a rule or in a `WITH` block. Each argument is a path, and the
macro gets the value at the path. A call passes one argument per `TAKES`. If it passes fewer, the runtime reads each
missing one from the path named like its parameter. In the code of an `EVAL`, `@name(arguments)` calls a macro with
values, see [2.3.3.5 EVAL code](#2335-eval-code).

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "half" {
            ENTRY {
                SET("bulb->watts", MACRO("share", "bulb->maxWatts", "mode"))
            }
        }
    }
    TRANSITIONS { }
    MACROS {
        MACRO "share" {
            TAKES("full", "number")
            TAKES("mode", "string")
            RETURNS("number")
            DEFINITION {
                EVAL { return $(full) / 4 if $(mode) == "eco" else $(full) / 2 }
            }
        }
    }
}
```

## 2.3.7 Histories

A history makes a state with inner states remember which of them was active when the state machine left it. When the
state machine enters the state again, it goes on to the remembered state. `SHALLOW HISTORY` remembers the inner state
directly in it, `DEEP HISTORY` the innermost state at any depth. The history is written after `INITIAL` and before
`STATE`.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        SHALLOW HISTORY STATE "on" {
            INITIAL STATE "full" { }
            STATE "dimmed" { }
        }
        STATE "off" { }
    }
    TRANSITIONS {
        TRANSITION "full" -> "dimmed" {
            CONDITION { EVENT("switch", "dim") }
        }
        TRANSITION "dimmed" -> "full" {
            CONDITION { EVENT("switch", "dim") }
        }
        TRANSITION "on" -> "off" {
            CONDITION { EVENT("switch", "press") }
        }
        TRANSITION "off" -> "on" {
            CONDITION { EVENT("switch", "press") }
        }
    }
}
```

The lamp starts at full power. A lamp that was switched off while dimmed comes on dimmed again.

## 2.3.8 Tick limits

A tick limit bounds how many ticks a state stays active. The block `TICK LIMIT { ... }` holds a delay, a timeout or
both, in either order.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "off" { }
        STATE "on" {
            TICK LIMIT {
                DELAY: 2 TICKS
                TIMEOUT: AFTER 20 TICKS TRANSITION TO "off"
            }
        }
    }
    TRANSITIONS {
        TRANSITION "off" -> "on" {
            CONDITION { EVENT("switch", "press") }
        }
        TRANSITION "on" -> "off" {
            CONDITION { EVENT("switch", "press") }
        }
    }
}
```

`DELAY: n TICKS` keeps the state machine in the state until the state was active for more than `n` ticks.
`TIMEOUT: AFTER n TICKS TRANSITION TO "state"` leads to the named state once the state was active for more than `n`
ticks. Here the lamp stays on for more than two ticks before a press can switch it off, and without a press it goes off
once it has been on for more than 20 ticks. A count is a whole number, and `TICK` and `TICKS` are read alike, so
`1 TICK` and `5 TICKS` are both fine.

## 2.3.9 Breakpoints

A breakpoint marks where the debugger of the IDE halts a run, see
[4.6 Debugging](https://github.com/karpfenproject/karpfen-IDE/blob/main/docs/reference/4.6-debugging.md). In a state,
`BREAKPOINT { ENTRY EXIT }` halts when the state machine enters the state, when it leaves it, or both. In a transition,
split or join, `BREAKPOINT { START END }` halts at the start of the transition, at its end, or both. A block names one
of its two words or both, in either order. In a transition the block comes before the `CONDITION` block.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "off" {
            BREAKPOINT { EXIT }
        }
        STATE "on" { }
    }
    TRANSITIONS {
        TRANSITION "off" -> "on" {
            BREAKPOINT { START END }
            CONDITION { EVENT("switch", "press") }
        }
    }
}
```

## 2.3.10 Optional features

Six parts of KStates are optional features. A tool decides which of them a text may use. The IDE keeps this choice in
the settings of a project, see
[4.1 Projects](https://github.com/karpfenproject/karpfen-IDE/blob/main/docs/reference/4.1-projects.md). The library
allows all of them unless it is told otherwise, see [2.5.6 Optional features](2.5-library.md#256-optional-features).

| Feature | Id | Constructs | The problem is reported at |
|---|---|---|---|
| Histories | `history` | `SHALLOW HISTORY`, `DEEP HISTORY` | `SHALLOW`, `DEEP` |
| Tick limits | `tickLimit` | `TICK LIMIT { ... }` | `TICK` |
| Breakpoints | `breakpoints` | `BREAKPOINT { ... }` in states, transitions, splits and joins | `BREAKPOINT` |
| Macros | `macros` | the `MACROS` block and every `MACRO(...)` call, also in a `WITH` block | `MACROS` once for the block, `MACRO` of each call |
| Splits and joins | `parallel` | `SPLIT` and `JOIN` | `SPLIT`, `JOIN` |
| Dynamic attachment | `attachment` | the attachable form of a state machine, the `ATTACH` clause, `EXCHANGE`, and `behaves after` in KMeta | `ATTACHABLE`, `ATTACH`, `EXCHANGE`, `behaves` |

When a feature is switched off, the text is still read as before, but each of its constructs is an error with the code
`kstates.feature-off`, or `kmeta.feature-off` for `behaves after` in a KMeta text. Switching a feature on again turns
these errors off. An `@name(...)` call in `EVAL` code is not a construct of the feature `macros`.

At run time, histories, tick limits and breakpoints take effect only where the runtime has the matching feature switched
on, see
[3.2 Runtime features](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/reference/3.2-features.md).
Without it, the state machine runs as if they were not written. Dynamic attachment needs no runtime feature: the
runtime always understands it.

## 2.3.11 State machine management and lifecycle

An attached state machine runs on one object that a run names by its key. That fits a lamp that exists from the start.
It does not fit objects that come and go while the model runs, such as the spare bulbs of the room, which a state
machine creates. For them a project writes attachable state machines and says in the model and in the actions which
object gets which one.

Use the attached form, `ATTACHED TO "Type"`, for the state machine of one known object, chosen when the project runs.
Use the attachable form, `"name" ATTACHABLE TO "Type", ...`, for behaviour that many objects share, objects that exist
from the start as well as objects that rules create. Each object gets an instance of its own, which starts in the
initial state. List several types when the same behaviour fits objects of several types; every path of the state machine
must then be valid from each of them.

`behaves after "name"` in the header of a KMeta type gives every object of the type an instance of the named state
machine: each object of the model at the start of a run, and each object a rule creates. Use it for the usual behaviour
of a type.

```kmeta
type "Bulb" "A light bulb that burns with watts, up to maxWatts" behaves after "glowing" {
    prop("maxWatts", "number")
    prop("watts", "number")
    prop("lit", "boolean")
}
type "Switch" "A wall switch" {
    prop("position", "string")
    prop("presses", list("string"))
}
type "Lamp" "A lamp with a bulb, wired to a switch" {
    prop("mode", "string")
    has("bulb", "Bulb")
    knows("control", "Switch")
}
type "Room" "The room the lamp stands in, with spare bulbs" {
    has("lamp", "Lamp")
    has("switch", "Switch")
    has("spares", list("Bulb"))
}
```

Every bulb glows while it has watts:

```kstates
STATEMACHINE "glowing" ATTACHABLE TO "Bulb" {
    STATES {
        INITIAL STATE "dark" {
            ENTRY { SET("lit", "false") }
        }
        STATE "lit" {
            ENTRY { SET("lit", "true") }
        }
    }
    TRANSITIONS {
        TRANSITION "dark" -> "lit" {
            CONDITION { EVAL { return $(watts) > 0 } }
        }
        TRANSITION "lit" -> "dark" {
            CONDITION { EVAL { return $(watts) == 0 } }
        }
    }
}
```

A bulb that blinks switches its light on every tick:

```kstates
STATEMACHINE "blinking" ATTACHABLE TO "Bulb" {
    STATES {
        INITIAL STATE "off" {
            ENTRY { SET("lit", "false") }
        }
        STATE "on" {
            ENTRY { SET("lit", "true") }
        }
    }
    TRANSITIONS {
        TRANSITION "off" -> "on" { }
        TRANSITION "on" -> "off" { }
    }
}
```

`ATTACH name` after a `SETOBJ` or `APPENDOBJ` on a `has` relation names the state machine of the object the rule
creates, in place of the one its type behaves after. Use it when a created object should start with other behaviour
than the usual one. `EXCHANGE("path", name)` ends the state machine of an object of the model and attaches an instance
of the named one, which starts in its initial state. Use it to change the behaviour of an object that exists already.
On an object without a state machine, `EXCHANGE` attaches the named one.

The state machine of the room adds a blinking spare bulb when the switch is pressed, and makes the bulb of the lamp
blink on the next press:

```kstates
STATEMACHINE ATTACHED TO "Room" {
    STATES {
        INITIAL STATE "waiting" { }
        STATE "stocked" {
            ENTRY {
                APPENDOBJ("self", "spares", MACRO("new bulb", "lamp->bulb->maxWatts")) ATTACH "blinking"
            }
        }
        STATE "party" {
            ENTRY {
                EXCHANGE("lamp->bulb", "blinking")
            }
        }
    }
    TRANSITIONS {
        TRANSITION "waiting" -> "stocked" {
            CONDITION { EVENT("switch", "press") }
        }
        TRANSITION "stocked" -> "party" {
            CONDITION { EVENT("switch", "press") }
        }
    }
    MACROS {
        MACRO "new bulb" {
            TAKES("watts", "number")
            RETURNS("Bulb")
            DEFINITION {
                EVAL { return {"maxWatts": $(watts), "watts": $(watts)} }
            }
        }
    }
}
```

The name after `ATTACH` and the second operand of `EXCHANGE` are values in the three forms of
[2.3.3.4 Values](#2334-values): a string is the name itself, and `EVAL { return $(mode) }` takes the name from the
model, or from a `WITH` binding by its name. The verifier checks a name written as a string: that an attachable state
machine of the project has it, and that the state machine lists the type of the object. A name that an `EVAL` or a
`MACRO` computes is checked when the action runs. `ATTACH` on a `knows` relation is an error, since that relation links
an object that exists already; `EXCHANGE` is the rule for such an object. [2.4 Checks](2.4-checks.md) lists the codes.

What happens at run time, when an instance starts, in which order the instances of a tick run, and what becomes of the
state machine of an object that is removed, is described in
[3.1.13 State machine management and lifecycle](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/reference/3.1-execution-semantics.md#3113-state-machine-management-and-lifecycle).

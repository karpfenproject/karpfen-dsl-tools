# 2.3 KStates

A KStates text is a state machine. Its states carry actions that read and write the model, and its transitions lead
from state to state when their conditions hold. A file has the extension `.kstates` and holds exactly one state
machine. The grammar of the language is `src/main/antlr/io/karpfen/dsl/grammar/kstates/Kstates.g4` in the
karpfen-dsl-tools repository.

What each construct does at run time, in every detail, is defined in
[3.1 Execution semantics](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/reference/3.1-execution-semantics.md)
in the reference of the runtime.

The examples of this section run on the lamp metamodel of [2 Modeling languages](2-modeling-languages.md), extended by
a list of spare bulbs in the room.

```kmeta
type "Bulb" "A light bulb that burns with watts, up to maxWatts" {
    prop("maxWatts", "number")
    prop("watts", "number")
    prop("lit", "boolean")
}
type "Switch" "A wall switch" {
    prop("position", "string")
    prop("presses", list("string"))
}
type "Lamp" "A lamp with a bulb, wired to a switch" {
    prop("mode", "string")
    has("bulb", "Bulb")
    knows("control", "Switch")
}
type "Room" "The room the lamp stands in, with spare bulbs" {
    has("lamp", "Lamp")
    has("switch", "Switch")
    has("spares", list("Bulb"))
}
```

## 2.3.1 The state machine

A text starts with `STATEMACHINE ATTACHED TO "Type"`, in which `Type` is a type of the domain metamodel. The braces
after this header hold the blocks `STATES`, `TRANSITIONS` and `MACROS` in this order. `STATES` and `TRANSITIONS` must
be written, but `TRANSITIONS` may be empty. `MACROS` may be left out.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "off" { }
    }
    TRANSITIONS { }
}
```

The state machine runs on one object of the type it is attached to, and a run chooses this object by its key. Every
path of the state machine starts at the object, except a path whose first key is one of the names listed in
[2.3.3.2 Paths](#2332-paths).

A text may instead start with `STATEMACHINE "name" ATTACHABLE TO "Type", ...`. Such an attachable state machine is a
definition with a name and one or more types. The name must be given, and each type may be listed only once. A run
does not attach an attachable state machine by a key. Instead the runtime builds an instance of it for each object that
gets it in one of the three ways of
[2.3.11 State machine management and lifecycle](#2311-state-machine-management-and-lifecycle): through a
`behaves after` on the type of the object, through an `ATTACH` clause or through an `EXCHANGE`. The state machine
`glowing` is attachable to bulbs.

```kstates
STATEMACHINE "glowing" ATTACHABLE TO "Bulb" {
    STATES {
        INITIAL STATE "dark" { }
    }
    TRANSITIONS { }
}
```

The third form, `STATEMACHINE "name" FRAGMENT`, is one of the fragments of [2.3.12 Pages](#2312-pages): a piece of a
state machine that runs inside a container state of another state machine.

## 2.3.2 States

`STATE "name" { ... }` defines a state. No two states of a state machine may have the same name, at whatever depth
they stand, and transitions refer to states by these names.

### 2.3.2.1 Nesting

A state may hold inner states. They are written inside its braces, after all other parts of the state. While an inner
state is active, the states around it are active too. Since the runtime tries the transitions of every active state, a
transition that starts at an outer state also applies while the state machine is in one of its inner states.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "off" { }
        STATE "on" {
            STATE "full" { }
            STATE "dimmed" { }
        }
    }
    TRANSITIONS {
        TRANSITION "off" -> "full" {
            CONDITION { EVENT("switch", "press") }
        }
        TRANSITION "full" -> "dimmed" {
            CONDITION { EVENT("switch", "dim") }
        }
        TRANSITION "on" -> "off" {
            CONDITION { EVENT("switch", "press") }
        }
    }
}
```

A press switches the lamp off from `full` as well as from `dimmed`, since the transition from `on` applies in both.

A transition into a state with inner states enters only that state and none of its inner states. That is why the
transition from `off` in the example names `full` as its target.

### 2.3.2.2 The initial state

The keyword `INITIAL` in front of `STATE` marks where the state machine starts. Exactly one state of a file carries the
mark. It may stand at any depth, and the rule is the same for a state machine and for a fragment. A file without a mark
or with two marks gets the error `kstates.initial-state-count`.

At the start the state machine enters a stack of states, the start stack, with the outermost state first. The start
stack is built level by level. On the top level the start takes the state that is marked or that holds the mark
somewhere inside it. If no state of the level is marked or holds the mark, the start takes the first state of the
level. While the chosen state has inner states, the start goes on below it by the same rule, and it stops at a state
without inner states.

Because the start follows the mark down through the levels, the mark may stand on an inner state. The state machine
then starts in the marked state and in every state
around it, no matter where these stand among their siblings.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        STATE "off" { }
        STATE "on" {
            STATE "full" { }
            INITIAL STATE "dimmed" { }
        }
    }
    TRANSITIONS {
        TRANSITION "dimmed" -> "full" {
            CONDITION { EVENT("switch", "dim") }
        }
        TRANSITION "on" -> "off" {
            CONDITION { EVENT("switch", "press") }
        }
        TRANSITION "off" -> "full" {
            CONDITION { EVENT("switch", "press") }
        }
    }
}
```

The start stack is `on`, `dimmed`. Although `off` is the first state of the top level, the start takes `on` because
`on` holds the mark. Inside `on` it takes the marked `dimmed`, even though `full` stands first.

If the marked state has inner states, the start goes on to its first inner state, and from there to the first inner
state of each level below.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "on" {
            STATE "full" {
                STATE "steady" { }
                STATE "flickering" { }
            }
            STATE "dimmed" { }
        }
        STATE "off" { }
    }
    TRANSITIONS {
        TRANSITION "steady" -> "flickering" {
            CONDITION { EVENT("service", "flicker") }
        }
        TRANSITION "full" -> "dimmed" {
            CONDITION { EVENT("switch", "dim") }
        }
        TRANSITION "on" -> "off" {
            CONDITION { EVENT("switch", "press") }
        }
        TRANSITION "off" -> "on" {
            CONDITION { EVENT("switch", "press") }
        }
    }
}
```

The start stack is `on`, `full`, `steady`.

For the start, a container state of [2.3.12 Pages](#2312-pages) counts as a state whose inner states are the states of
its fragment. When the start stack reaches a container state, either
because the container state is marked or because it stands first on the way down, the start goes on with the start of
the fragment. Inside the fragment the start is chosen by the mark of the fragment, by the same rule. The following
examples use this fragment, whose mark is on `dimmed`.

```kstates
STATEMACHINE "dimmer" FRAGMENT {
    STATES {
        STATE "full" { }
        INITIAL STATE "dimmed" { }
        FINAL STATE "dark" { }
    }
    TRANSITIONS {
        TRANSITION "dimmed" -> "full" {
            CONDITION { EVENT("switch", "dim") }
        }
        TRANSITION "full" -> "dark" {
            CONDITION { EVENT("switch", "dim") }
        }
    }
}
```

When the container state is marked, the state machine starts inside its fragment.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        STATE "off" { }
        INITIAL CONTAINER STATE "on" USE "dimmer" { }
    }
    TRANSITIONS {
        TRANSITION "on" -> "off" {
            CONDITION { EVENT("switch", "press") }
        }
        TRANSITION "off" -> "on" {
            CONDITION { EVENT("switch", "press") }
        }
    }
}
```

The start stack is `on`, `on/dimmed`. The name `on/dimmed` is the state `dimmed` of the fragment with the name of its
container state in front, by the naming rule of [2.3.12.3 Names](#23123-names).

The start goes on in the same way when it reaches an unmarked container state on its way down.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "on" {
            CONTAINER STATE "dimming" USE "dimmer" { }
            STATE "bright" { }
        }
        STATE "off" { }
    }
    TRANSITIONS {
        TRANSITION "dimming" -> "bright" {
            CONDITION { DONE }
        }
        TRANSITION "on" -> "off" {
            CONDITION { EVENT("switch", "press") }
        }
        TRANSITION "off" -> "on" {
            CONDITION { EVENT("switch", "press") }
        }
    }
}
```

The start stack is `on`, `dimming`, `dimming/dimmed`.

The mark of a fragment belongs to the fragment, and the state machine that uses the fragment does not see it. It is not
the mark of that state machine, and it does not pull the start of the state machine into the container
state. It only says where the fragment starts each time its container state is entered.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "off" { }
        CONTAINER STATE "on" USE "dimmer" { }
    }
    TRANSITIONS {
        TRANSITION "off" -> "on" {
            CONDITION { EVENT("switch", "press") }
        }
        TRANSITION "on" -> "off" {
            CONDITION { EVENT("switch", "press") }
        }
    }
}
```

The start stack is `off`. A press enters `on` and at once `on/dimmed`, and every later press from `off` does the same.
If `on` had its inner states written in its braces, the mark on `dimmed` would be the one mark of the file. The state
machine would then start in `on`, `dimmed`, the start stack of the first example.

The start goes down into a state whose inner states are written in its braces, while a transition into such a state
enters only the state itself and none of its inner states, by the rule of [2.3.2.1 Nesting](#2321-nesting). Every
entry into a container state, by the start or by a transition, goes on with the start of its fragment. The one
exception is a container state whose history, as described in [2.3.7 Histories](#237-histories), remembers a state of
its fragment: it goes on with the remembered state.

The reference of the runtime describes what runs when the states are entered and in which tick. The general rules are
in
[3.1.3 Active states](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/reference/3.1-execution-semantics.md#313-active-states),
every way of entering a state is covered in
[3.1.15 Where the engine goes](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/reference/3.1-execution-semantics.md#3115-where-the-engine-goes),
and container states have their own section,
[3.1.14 Pages](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/reference/3.1-execution-semantics.md#3114-pages).

### 2.3.2.3 Parts of a state

The parts of a state are all optional and stand in the order of this table.

| Part | Described in |
|---|---|
| `BREAKPOINT { ... }` | [2.3.9 Breakpoints](#239-breakpoints) |
| `TICK LIMIT { ... }` | [2.3.8 Tick limits](#238-tick-limits) |
| `ENTRY { ... }` | [2.3.3.1 Entry and do blocks](#2331-entry-and-do-blocks) |
| `DO { ... }` | [2.3.3.1 Entry and do blocks](#2331-entry-and-do-blocks) |
| The inner states | [2.3.2.1 Nesting](#2321-nesting) |

The keyword `STATE` may have `INITIAL` in front of it, followed by one of the histories of
[2.3.7 Histories](#237-histories), `SHALLOW HISTORY` or `DEEP HISTORY`. Both are optional. Directly in front of
`STATE` may stand `CONTAINER` or `FINAL`. They make the container states and final states of
[2.3.12 Pages](#2312-pages), which have fewer parts than a plain state.

## 2.3.3 Actions

### 2.3.3.1 Entry and do blocks

`ENTRY { ... }` holds the actions that a state runs once, when the state machine enters it. `DO { ... }` holds the
actions that the state runs in every tick in which it is the innermost active state. Both blocks may hold action rules,
`IF IN SCOPE` blocks and `WITH` blocks, and these run in the order in which they are written.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "off" {
            ENTRY {
                SET("mode", "off")
                SET("bulb->watts", "0")
            }
        }
        STATE "warming up" {
            ENTRY {
                SET("mode", "on")
            }
            DO {
                SET("bulb->watts", EVAL { return min($(bulb->watts) + 10, $(bulb->maxWatts)) })
            }
        }
    }
    TRANSITIONS {
        TRANSITION "off" -> "warming up" {
            CONDITION { EVENT("switch", "press") }
        }
    }
}
```

While the lamp is in `warming up`, every tick gives the bulb 10 W more until it reaches its maximum. There is no block
for actions on leaving a state.

### 2.3.3.2 Paths

A path names a property or a relation. It is a string of keys joined by `->`, and it starts at the object the state
machine runs on. On the lamp, `"mode"` is the mode of the lamp, `"bulb->watts"` the watts of its bulb, and
`"control->position"` the position of the switch that the lamp knows. A path follows `has` and `knows` relations alike.
When a path goes on after a list relation, it goes on from the first object of the list.

Because a path is split at every `->`, a key that is used in paths should not contain `->`. The spaces around each key
are dropped.

A path starts somewhere else when its first key is one of the following names.

| First key | Where the path starts | Described in |
|---|---|---|
| `event` | At the payload of the event in scope. | [2.3.5 Events](#235-events) |
| The name of a `WITH` block around it | At the result of its macro. | [2.3.3.7 WITH blocks](#2337-with-blocks) |
| A parameter of the macro, in the code of a macro | At the value of the parameter. | [2.3.6 Macros](#236-macros) |

In the code of a macro, a path whose first key is not a parameter names a local variable of the code, and the runtime
leaves it to Python.

### 2.3.3.3 Action rules

An action rule names an operation and its operands in parentheses. The first operand is always a string.

| Rule | What it does |
|---|---|
| `SET("path", value)` | Writes the value into a property that is not a list. |
| `APPEND("path", value)` | Adds the value at the end of a list property. |
| `SETLIST("path", value)` | Replaces a list property with the list that its `EVAL` or `MACRO` returns. |
| `DROPLIST("path")` | Empties a list property. |
| `SETOBJ("source", "relation", target)` | Sets the relation of the object at `source`, which holds one object, to the target. |
| `APPENDOBJ("source", "relation", target)` | Adds the target to the list relation of the object at `source`. |
| `DROPOBJ("path")` | Removes the object at the path from the model, with every reference to it. |
| `EVENT("domain", name)` | Raises an event of the name in the domain, without payload. |
| `EXCHANGE("path", name)` | Ends the state machine of the object at the path and attaches an instance of the attachable state machine of the name. |

The source of `SETOBJ` and `APPENDOBJ` is a path to an object, and `"self"` and `""` name the object the state machine
runs on. The target of a `has` relation must be a new object built by a `MACRO` or an `EVAL`. The target of a `knows`
relation must be an object that is already in the model. It is given either as a path to that object or as a macro
that returns `reference("Type")`. Every operation except `EVENT` may also be written in lower case, for example `set`.

In the following state machine the lamp empties, extends and replaces the list of presses of its switch, and it raises
the event `switched on` in the domain `lamp`.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "off" {
            ENTRY {
                SET("mode", "off")
                DROPLIST("control->presses")
            }
        }
        STATE "on" {
            ENTRY {
                SET("mode", "on")
                APPEND("control->presses", "on")
                EVENT("lamp", "switched on")
            }
        }
        STATE "reset" {
            ENTRY {
                SETLIST("control->presses", EVAL { return ["reset"] })
            }
        }
    }
    TRANSITIONS {
        TRANSITION "off" -> "on" {
            CONDITION { EVENT("switch", "press") }
        }
        TRANSITION "on" -> "reset" {
            CONDITION { EVENT("switch", "press") }
        }
        TRANSITION "reset" -> "off" { }
    }
}
```

The next state machine is attached to the room and changes relations. It wires the lamp to the switch, adds a new
spare bulb and removes the bulb from the lamp.

```kstates
STATEMACHINE ATTACHED TO "Room" {
    STATES {
        INITIAL STATE "rewiring" {
            ENTRY {
                SETOBJ("lamp", "control", "switch")
                APPENDOBJ("self", "spares", MACRO("new bulb", "lamp->bulb->watts"))
                DROPOBJ("lamp->bulb")
            }
        }
    }
    TRANSITIONS { }
    MACROS {
        MACRO "new bulb" {
            TAKES("watts", "number")
            RETURNS("Bulb")
            DEFINITION {
                EVAL { return {"watts": $(watts)} }
            }
        }
    }
}
```

A `SETOBJ` or `APPENDOBJ` on a `has` relation may end with `ATTACH name` after its parentheses. The clause names the
attachable state machine that the new object gets. `EXCHANGE("path", name)` replaces the state machine of an object
that is already in the model. In both rules the name is a value. A string is taken as the name itself and not as a
path, and an `EVAL` or a `MACRO` must return the name as a string. `ATTACH` may also be written `attach`.
[2.3.11 State machine management and lifecycle](#2311-state-machine-management-and-lifecycle) shows both rules at
work.

### 2.3.3.4 Values

The last operand of a rule, its value, has one of three forms.

| Form | Example | Value |
|---|---|---|
| A string | `"40"` | For `SET` and `APPEND`, the text read as the type of the property: a number, `true` or `false`, or any text. For `SETOBJ` and `APPENDOBJ`, a path to an object. For `EVENT`, the name of the event. |
| `EVAL { code }` | `EVAL { return $(bulb->maxWatts) / 2 }` | What the code returns ([2.3.3.5 EVAL code](#2335-eval-code)). |
| `MACRO("name", "path", ...)` | `MACRO("half", "bulb->maxWatts")` | What the macro returns ([2.3.6 Macros](#236-macros)). |

A number or a boolean is also written as a string, for example `SET("bulb->watts", "0")`. Without the quotes the rule
is a syntax error.

### 2.3.3.5 EVAL code

`EVAL { ... }` holds code that the runtime runs as Python. It can be the value of a rule, a clause of a condition or the
definition of a macro, and it returns its result with `return`.

The runtime prepares the code before it runs it. Each `$(path)` becomes the current value at the path:
`$(bulb->watts) + 10` is 10 more than the watts the bulb has at this moment. Each `@name(arguments)` becomes
a call of the macro `name`, with one argument for each `TAKES` of the macro.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "dimmed" {
            ENTRY {
                SET("bulb->watts", EVAL {
                    full = $(bulb->maxWatts)
                    return @half(full)
                })
            }
        }
    }
    TRANSITIONS { }
    MACROS {
        MACRO "half" {
            TAKES("watts", "number")
            RETURNS("number")
            DEFINITION {
                EVAL { return $(watts) / 2 }
            }
        }
    }
}
```

The code may run over several lines. Because the library reads it as KStates text up to the closing brace, the braces
in the code must pair up. Braces and `//` inside the string literals of the code do not count. Outside string
literals, `//` starts a KStates comment that runs to the end of the line. In `return a // b` the reader drops `// b`,
together with a closing brace that stands after it on the same line. Write `int(a / b)` for the integer division and
`#` for a Python comment.

### 2.3.3.6 IF IN SCOPE blocks

`IF IN SCOPE("path", ...) { ... }` runs the actions inside only if every path it names can be read at this moment. A
path that starts with `event` can be read if an event is in scope and its payload has that field. Any other path can be
read if it leads to a value from the object the state machine runs on. The block lets a state read a field of the
payload that not every way into the state brings along. In the following example the state machine enters `on` either
on a `dim` event, whose payload carries `bright`, or on a `press`, which carries no payload. The block reads `bright`
only after a `dim`.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "off" { }
        STATE "on" {
            ENTRY {
                SET("bulb->watts", EVAL { return $(bulb->maxWatts) })
                IF IN SCOPE("event->bright") {
                    SET("bulb->lit", EVAL { return $(event->bright) })
                }
            }
        }
    }
    TRANSITIONS {
        TRANSITION "off" -> "on" {
            CONDITION { EVENT("switch", "dim") }
        }
        TRANSITION "off" -> "on" {
            CONDITION { EVENT("switch", "press") }
        }
        TRANSITION "on" -> "off" {
            CONDITION { EVENT("switch", "press") }
        }
    }
}
```

Several paths are separated by commas, and the block runs only if all of them can be read. Blocks may be nested.

### 2.3.3.7 WITH blocks

`WITH MACRO("name", ...) AS "binding" { ... }` runs the macro once and gives its result the name `binding` for the
actions inside the block. The code of an `EVAL` inside the block reads the result as `$(binding)`. If the result is an
object, the code reads one of its values as `$(binding->key)`. The paths that a macro call inside the block passes as
arguments may start with the name as well. `with` and `as` may also be written in lower case.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "on" {
            ENTRY {
                WITH MACRO("brightest", "bulb->maxWatts") AS "best" {
                    SET("bulb->watts", EVAL { return $(best) })
                    SET("bulb->lit", EVAL { return $(best) > 0 })
                }
            }
        }
    }
    TRANSITIONS { }
    MACROS {
        MACRO "brightest" {
            TAKES("limit", "number")
            RETURNS("number")
            DEFINITION {
                EVAL { return $(limit) }
            }
        }
    }
}
```

Because the macro runs only once for the block, both rules see the same result, even when the macro would return
another value each time it runs.

## 2.3.4 Transitions

`TRANSITION "from" -> "to" { ... }` leads from one state to another, or from a state back to the same state. Its
braces may hold a `BREAKPOINT` block followed by a `CONDITION` block. A transition without a `CONDITION` block fires
whenever the runtime tries it.

### 2.3.4.1 Conditions

`CONDITION { ... }` holds one clause or more, and the transition fires only if all of them hold. The runtime checks the
clauses from top to bottom and stops at the first one that fails.

| Clause | Holds when |
|---|---|
| `EVENT("domain", "name")` | An event of this name waits in this domain ([2.3.5 Events](#235-events)). |
| `VALUE("path")` | The boolean property at the path is true, or the string property at the path is `true` in any case. `VALUE("true")` always holds and `VALUE("false")` never. |
| `EVAL { code }` | The code returns true. |
| `DONE` | The container state that the transition leaves has reached a final state of its fragment ([2.3.12 Pages](#2312-pages)). |

A condition has at most one `EVENT` clause. Write it first, since the clauses after it can read the payload of the
event.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "on" {
            STATE "dimmer" {
                ENTRY {
                    SET("bulb->watts", EVAL { return $(bulb->watts) - 10 })
                }
            }
        }
    }
    TRANSITIONS {
        TRANSITION "on" -> "dimmer" {
            CONDITION {
                EVENT("switch", "dim")
                EVAL { return not $(event->bright) }
                EVAL { return $(bulb->watts) - 10 >= 0 }
            }
        }
    }
}
```

A `dim` event whose payload has `bright` set to false makes the lamp 10 W dimmer. The last clause,
`$(bulb->watts) - 10 >= 0`, lets the transition fire only while the bulb has at least 10 W.

### 2.3.4.2 Order and NOT LOOPING

The runtime tries the transitions of the innermost active state first and those of the states around it afterwards.
The transitions of one state are tried in the order in which they are written. Because the first one whose condition
holds fires, the order of the `TRANSITIONS` block is a priority.

`NOT LOOPING`, written after the target, keeps a transition from firing twice in a row. When the runtime skips a
transition for this reason, it tries the next one. The keyword has an effect only on a `TRANSITION`. A split or a join
accepts it, but it has no effect there.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "on" {
            DO {
                SET("bulb->watts", EVAL { return $(bulb->watts) - 1 })
            }
        }
        STATE "check" { }
    }
    TRANSITIONS {
        TRANSITION "on" -> "on" NOT LOOPING {
            CONDITION { VALUE("bulb->lit") }
        }
        TRANSITION "on" -> "check" { }
        TRANSITION "check" -> "on" { }
    }
}
```

While the bulb is lit, the state machine enters `on` again, but never twice in a row. In between it takes the
transition to `check` and comes back from there.

### 2.3.4.3 Splits and joins

A split leads from one state into two or more states that are then active side by side, each in a branch of its own. A
join leads from such states back into one state.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "off" { }
        STATE "bulb test" { }
        STATE "switch test" { }
        STATE "tested" { }
    }
    TRANSITIONS {
        SPLIT "off" -> "bulb test", "switch test" {
            CONDITION { EVENT("service", "test") }
        }
        JOIN "bulb test", "switch test" -> "tested" { }
    }
}
```

`SPLIT "from" -> "a", "b", ...` names two targets or more, and `JOIN "a", "b", ... -> "to"` names two sources or more.
A split names each of its targets only once, and a join each of its sources. Both take `NOT LOOPING`, a `BREAKPOINT`
block and a `CONDITION` block in the same way as a `TRANSITION`.

The runtime takes a split only while no branches are active. It takes a join only when each of its sources is active
in a branch of its own, and it tries the join before the transitions of the branches.
[3.1.8 Splits and joins](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/reference/3.1-execution-semantics.md#318-splits-and-joins)
explains how the branches run.

## 2.3.5 Events

An event has a domain and a name, and it may carry a payload. The domain and the name are any strings. In the examples
of this chapter, presses arrive in the domain `switch` and the smash in the domain `service`.

Events come from the `EVENT` actions of state machines and from outside the runtime. A program outside the runtime
first registers as a client with the route of
[3.4.6 Clients](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/reference/3.4-http-api.md#346-clients)
and then sends each event over the WebSocket in the message of
[3.5.2 Sending events](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/reference/3.5-websocket.md#352-sending-events).
The bridges of the IDE turn HTTP, MQTT and ROS messages into events by the inbound routes of
[4.7 Bridges](https://github.com/karpfenproject/karpfen-IDE/blob/main/docs/reference/4.7-bridges.md).

The clause `EVENT("domain", "name")` holds when an event of this domain and name waits. The event that fires the
transition is then in scope. The clauses after the `EVENT` clause, the state that the transition leads to and the
states inside that state can read its payload with paths that start with `event`, such as `event->bright` or
`$(event->bright)`. The event stays in scope while that state is active.

The payload of an event has the type of the same name in the event metamodel. In the event metamodel of
[2.1.7 Event definitions](2.1-kmeta.md#217-event-definitions) the event `dim` carries the boolean `bright`, and the
following state machine reads it.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "on" { }
        STATE "brighter" {
            ENTRY {
                SET("bulb->watts", EVAL { return $(bulb->watts) + 10 })
            }
        }
    }
    TRANSITIONS {
        TRANSITION "on" -> "brighter" {
            CONDITION {
                EVENT("switch", "dim")
                VALUE("event->bright")
            }
        }
        TRANSITION "brighter" -> "on" { }
    }
}
```

## 2.3.6 Macros

A macro is a named piece of code with typed parameters. The block `MACROS` at the end of a state machine holds the
macros. Each of them is written as `MACRO "name" { ... }` with the following parts in this order.

1. `TAKES("parameter", type)` for each parameter, none or more
2. `RETURNS(type)`, exactly once
3. `DEFINITION { EVAL { code } }`, exactly once

| Type | Meaning |
|---|---|
| `"string"`, `"number"`, `"boolean"` | A primitive value. |
| `"Type"` | An object of a type of the domain metamodel or of the event metamodel. As a result, a new object. |
| `list("type")` | A list of values of the type. |
| `reference("Type")` | Only in `RETURNS`: an object that is already part of the model. |

The code reads a parameter as `$(parameter)`, and a value of an object parameter as `$(parameter->key)`. A macro that
returns a new object returns a Python dictionary of the values of that object, such as `{"watts": 40}`. The macro
`new bulb` in the second example of [2.3.3.3 Action rules](#2333-action-rules) does this.

`MACRO("name", "path", ...)` calls a macro as the value of a rule or in a `WITH` block. Each argument is a path, and the
macro gets the value at that path. A call passes one argument for each `TAKES`. If it passes fewer, the runtime reads
each missing argument from the path that has the name of its parameter. Inside `EVAL` code a call is written
`@name(arguments)` and passes values in place of paths. [2.3.3.5 EVAL code](#2335-eval-code) has an example.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "half" {
            ENTRY {
                SET("bulb->watts", MACRO("share", "bulb->maxWatts", "mode"))
            }
        }
    }
    TRANSITIONS { }
    MACROS {
        MACRO "share" {
            TAKES("full", "number")
            TAKES("mode", "string")
            RETURNS("number")
            DEFINITION {
                EVAL { return $(full) / 4 if $(mode) == "eco" else $(full) / 2 }
            }
        }
    }
}
```

## 2.3.7 Histories

A history makes a state with inner states remember which of them was active when the state machine left it. When the
state machine enters the state again, it goes on to the remembered state. `SHALLOW HISTORY` remembers the inner state
on the level directly below the state, and `DEEP HISTORY` remembers the innermost state at any depth. The history is
written after `INITIAL` and before `STATE`.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        SHALLOW HISTORY STATE "on" {
            INITIAL STATE "full" { }
            STATE "dimmed" { }
        }
        STATE "off" { }
    }
    TRANSITIONS {
        TRANSITION "full" -> "dimmed" {
            CONDITION { EVENT("switch", "dim") }
        }
        TRANSITION "dimmed" -> "full" {
            CONDITION { EVENT("switch", "dim") }
        }
        TRANSITION "on" -> "off" {
            CONDITION { EVENT("switch", "press") }
        }
        TRANSITION "off" -> "on" {
            CONDITION { EVENT("switch", "press") }
        }
    }
}
```

The lamp starts at full power. If it was switched off while dimmed, it comes on dimmed again.

## 2.3.8 Tick limits

A tick limit bounds how many ticks a state stays active. The block `TICK LIMIT { ... }` holds a delay, a timeout or
both, in either order.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "off" { }
        STATE "on" {
            TICK LIMIT {
                DELAY: 2 TICKS
                TIMEOUT: AFTER 20 TICKS TRANSITION TO "off"
            }
        }
    }
    TRANSITIONS {
        TRANSITION "off" -> "on" {
            CONDITION { EVENT("switch", "press") }
        }
        TRANSITION "on" -> "off" {
            CONDITION { EVENT("switch", "press") }
        }
    }
}
```

`DELAY: n TICKS` keeps the state machine in the state until the state has been active for more than `n` ticks.
`TIMEOUT: AFTER n TICKS TRANSITION TO "state"` leads to the named state as soon as the state has been active for more
than `n` ticks. In the example the lamp stays on for more than two ticks before a press can switch it off. Without a
press it goes off once it has been on for more than 20 ticks.

A count is a whole number. `TICK` and `TICKS` are the same keyword, and both `1 TICK` and `5 TICKS` may be written.

## 2.3.9 Breakpoints

A breakpoint marks a place where the debugger of
[4.6 Debugging](https://github.com/karpfenproject/karpfen-IDE/blob/main/docs/reference/4.6-debugging.md) halts a run in
the IDE.

In a state the block is `BREAKPOINT { ENTRY EXIT }`, and the run halts when the state machine enters the state, when it
leaves it, or in both cases. In a transition, a split or a join the block is `BREAKPOINT { START END }`, and the run
halts at the start of the transition, at its end, or at both. A block names one of its two words or both, in either
order. In a transition the block comes before the `CONDITION` block.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "off" {
            BREAKPOINT { EXIT }
        }
        STATE "on" { }
    }
    TRANSITIONS {
        TRANSITION "off" -> "on" {
            BREAKPOINT { START END }
            CONDITION { EVENT("switch", "press") }
        }
    }
}
```

## 2.3.10 Optional features

Five parts of KStates are optional features, and the tool that reads a text decides which of them the text may use.
The IDE keeps this choice in the project settings of
[4.1.7 Language features](https://github.com/karpfenproject/karpfen-IDE/blob/main/docs/reference/4.1-projects.md#417-language-features).
A program that uses the library passes its choice to the reader as in
[2.5.6 Optional features](2.5-library.md#256-optional-features). Without a choice the library allows all five.

| Feature | Id | Constructs | The problem is reported at |
|---|---|---|---|
| Histories | `history` | `SHALLOW HISTORY`, `DEEP HISTORY` | `SHALLOW`, `DEEP` |
| Tick limits | `tickLimit` | `TICK LIMIT { ... }` | `TICK` |
| Breakpoints | `breakpoints` | `BREAKPOINT { ... }` in states, transitions, splits and joins | `BREAKPOINT` |
| Macros | `macros` | the `MACROS` block and every `MACRO(...)` call, also in a `WITH` block | `MACROS` once for the block, `MACRO` of each call |
| Splits and joins | `parallel` | `SPLIT` and `JOIN` | `SPLIT`, `JOIN` |

When a feature is switched off, the text is still read as before, but each construct of the feature is an error with
the code `kstates.feature-off`. Switching the feature on again removes these errors. An `@name(...)` call in `EVAL`
code is not a construct of the feature `macros`.

At run time, histories, tick limits and breakpoints take effect only where the runtime has the matching feature of
[3.2 Runtime features](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/reference/3.2-features.md)
switched on. Without it the state machine runs as if they were not written.

The dynamic attachment of
[2.3.11 State machine management and lifecycle](#2311-state-machine-management-and-lifecycle) and the pages of
[2.3.12 Pages](#2312-pages) are not optional features. A text may always use fragments, container states, final
states and `DONE`, and the runtime always understands them.

## 2.3.11 State machine management and lifecycle

An attached state machine runs on the one object that a run names by its key. This suits a lamp that exists from the
start. It does not suit objects that come and go while the model runs, such as the spare bulbs of the room, because a
state machine creates them during the run and the run cannot name them in advance. For such objects a project writes
attachable state machines and says in the metamodel and in the actions which object gets which state machine.

The attached form, `ATTACHED TO "Type"`, is meant for the state machine of one known object that is chosen when the
project runs. The attachable form, `"name" ATTACHABLE TO "Type", ...`, is meant for behaviour that many objects share,
whether they exist from the start or are created by rules. Each of these objects gets an instance of its own, and every
instance starts in the initial state. When the same behaviour fits objects of several types, list all of these types.
Every path of the state machine must then be valid from each of them, and the verifier checks the paths once for each
type.

`behaves after "name"` in the header of a KMeta type gives every object of the type an instance of the named state
machine. This includes each object of the model at the start of a run and each object that a rule creates later. The
clause is the place for the usual behaviour of a type.

```kmeta
type "Bulb" "A light bulb that burns with watts, up to maxWatts" behaves after "glowing" {
    prop("maxWatts", "number")
    prop("watts", "number")
    prop("lit", "boolean")
}
type "Switch" "A wall switch" {
    prop("position", "string")
    prop("presses", list("string"))
}
type "Lamp" "A lamp with a bulb, wired to a switch" {
    prop("mode", "string")
    has("bulb", "Bulb")
    knows("control", "Switch")
}
type "Room" "The room the lamp stands in, with spare bulbs" {
    has("lamp", "Lamp")
    has("switch", "Switch")
    has("spares", list("Bulb"))
}
```

With the state machine `glowing`, every bulb glows while it has watts.

```kstates
STATEMACHINE "glowing" ATTACHABLE TO "Bulb" {
    STATES {
        INITIAL STATE "dark" {
            ENTRY { SET("lit", "false") }
        }
        STATE "lit" {
            ENTRY { SET("lit", "true") }
        }
    }
    TRANSITIONS {
        TRANSITION "dark" -> "lit" {
            CONDITION { EVAL { return $(watts) > 0 } }
        }
        TRANSITION "lit" -> "dark" {
            CONDITION { EVAL { return $(watts) == 0 } }
        }
    }
}
```

A bulb with the state machine `blinking` switches its light at every tick.

```kstates
STATEMACHINE "blinking" ATTACHABLE TO "Bulb" {
    STATES {
        INITIAL STATE "off" {
            ENTRY { SET("lit", "false") }
        }
        STATE "on" {
            ENTRY { SET("lit", "true") }
        }
    }
    TRANSITIONS {
        TRANSITION "off" -> "on" { }
        TRANSITION "on" -> "off" { }
    }
}
```

`ATTACH name` after a `SETOBJ` or `APPENDOBJ` on a `has` relation names the state machine of the object that the rule
creates. The new object gets this state machine in place of the one its type behaves after. Use the clause when a
created object should start with other behaviour than the usual one.

`EXCHANGE("path", name)` ends the state machine of an object of the model and attaches an instance of the named state
machine. The new instance starts in its initial state. Use the rule to change the behaviour of an object that exists
already. On an object without a state machine, `EXCHANGE` simply attaches the named one.

The following state machine of the room adds a blinking spare bulb when the switch is pressed. On the next press it
makes the bulb of the lamp blink as well.

```kstates
STATEMACHINE ATTACHED TO "Room" {
    STATES {
        INITIAL STATE "waiting" { }
        STATE "stocked" {
            ENTRY {
                APPENDOBJ("self", "spares", MACRO("new bulb", "lamp->bulb->maxWatts")) ATTACH "blinking"
            }
        }
        STATE "party" {
            ENTRY {
                EXCHANGE("lamp->bulb", "blinking")
            }
        }
    }
    TRANSITIONS {
        TRANSITION "waiting" -> "stocked" {
            CONDITION { EVENT("switch", "press") }
        }
        TRANSITION "stocked" -> "party" {
            CONDITION { EVENT("switch", "press") }
        }
    }
    MACROS {
        MACRO "new bulb" {
            TAKES("watts", "number")
            RETURNS("Bulb")
            DEFINITION {
                EVAL { return {"maxWatts": $(watts), "watts": $(watts)} }
            }
        }
    }
}
```

The name after `ATTACH` and the second operand of `EXCHANGE` are values, and they may take each of the three forms of
[2.3.3.4 Values](#2334-values). A string is the name itself. An `EVAL` can take the name from the model, as
`EVAL { return $(mode) }` does, or from a `WITH` binding by the name of the binding.

The verifier checks a name that is written as a string. It checks that an attachable state machine of the project has
this name and that this state machine lists the type of the object. A name that an `EVAL` or a `MACRO` computes is
checked only when the action runs.

`ATTACH` on a `knows` relation is an error, because such a relation links an object that exists already and the rule
creates no object. To give an existing object another state machine, use `EXCHANGE`. The codes of these problems are
listed in [2.4.6 Project](2.4-checks.md#246-project).

[3.1.13 State machine management and lifecycle](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/reference/3.1-execution-semantics.md#3113-state-machine-management-and-lifecycle)
describes what happens at run time: when an instance starts, in which order the instances of a tick run, and what
becomes of the state machine of an object that is removed.

## 2.3.12 Pages

A state machine grows long when it holds every step of a lamp, its self test included. Pages split such a state
machine into several files. A fragment holds a piece of behaviour, such as the self test, in a file of its own, and a
container state of another state machine runs the fragment as its inner states. The state machine and the fragments it
uses, directly or through other fragments, form a composition. Before the composition runs, the library flattens it
into one state machine.

### 2.3.12.1 Fragments and final states

A fragment starts with `STATEMACHINE "name" FRAGMENT`. It names no type, because it runs on the object of the state
machine that uses it, and its paths start at that object. Its body has the same blocks as that of any state machine,
`STATES`, `TRANSITIONS` and `MACROS`. Exactly one of its states is `INITIAL`, and at least one state on its top level
is a final state.

`FINAL STATE "name" { }` marks an end of the fragment. A final state stands only on the top level of a fragment. It has
no actions, no inner states, no tick limit and no history, and it is never `INITIAL`. Its braces may hold a
`BREAKPOINT` block and nothing else. No transition, split or join may leave a final state. The state machine stays in it
until a transition of the container state leads out.

The fragment `bulb test` powers the bulb at half its maximum. It passes once the bulb is lit, and it fails on a smash.

```kstates
STATEMACHINE "bulb test" FRAGMENT {
    STATES {
        INITIAL STATE "powered" {
            ENTRY {
                SET("bulb->watts", MACRO("half", "bulb->maxWatts"))
            }
        }
        FINAL STATE "passed" { }
        FINAL STATE "failed" { }
    }
    TRANSITIONS {
        TRANSITION "powered" -> "passed" {
            CONDITION { VALUE("bulb->lit") }
        }
        TRANSITION "powered" -> "failed" {
            CONDITION { EVENT("service", "smash") }
        }
    }
    MACROS {
        MACRO "half" {
            TAKES("watts", "number")
            RETURNS("number")
            DEFINITION {
                EVAL { return $(watts) / 2 }
            }
        }
    }
}
```

### 2.3.12.2 Container states and DONE

`CONTAINER STATE "name" USE "fragment" { }` runs the named fragment. Since the fragment does the work, a container
state has no `ENTRY` block, no `DO` block and no inner states of its own. Its braces may hold a `BREAKPOINT` block and a
`TICK LIMIT` block, and like any other state it may be `INITIAL` and carry a history. A container state may stand at
any depth, on the top level as well as inside another state or inside a fragment. A fragment may not use itself, neither
directly nor through other fragments.

Entering a container state starts its fragment in the same way as a state machine starts, by the rule of
[2.3.2.2 The initial state](#2322-the-initial-state). The state machine enters the marked state of the fragment
together with the states around it. Once a container state with a history of [2.3.7 Histories](#237-histories)
remembers a state, each later entry goes on with that state in place of the start.

Because the container state is active around the fragment while the fragment runs, its transitions apply in every
state of the fragment, just as the transitions of a state apply in its inner states. A transition that
leaves the container state ends the fragment.

The clause `DONE` holds when the container state that the transition leaves has reached a final state of its fragment.
It takes no arguments and stands on a `TRANSITION` or a `SPLIT` whose source is a container state.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "off" { }
        CONTAINER STATE "self test" USE "bulb test" {
            TICK LIMIT {
                TIMEOUT: AFTER 50 TICKS TRANSITION TO "off"
            }
        }
        STATE "on" { }
    }
    TRANSITIONS {
        TRANSITION "off" -> "self test" {
            CONDITION { EVENT("service", "test") }
        }
        TRANSITION "self test" -> "on" {
            CONDITION { DONE }
        }
        TRANSITION "self test" -> "off" {
            CONDITION { EVENT("switch", "press") }
        }
    }
}
```

On a test event the lamp runs the bulb test. When the test has reached `passed` or `failed`, the lamp goes on to `on`. A
press ends the test early, and so does the timeout after 50 ticks.

Because `DONE` does not tell the final states apart, a fragment that can end in several ways writes the outcome into
the model in its states, where the transitions of the container state read it.

On a `JOIN`, `DONE` concerns every source that is a container state, and it holds when each of them has reached a
final state. Sources that are not container states do not count for it. At least one source of the join must be a
container state. The following example runs two fragments side by side, with a split into two container states and a
join that waits until both are done. The second fragment waits for a press of the switch.

```kstates
STATEMACHINE "switch test" FRAGMENT {
    STATES {
        INITIAL STATE "waiting" { }
        FINAL STATE "pressed" { }
    }
    TRANSITIONS {
        TRANSITION "waiting" -> "pressed" {
            CONDITION { EVENT("switch", "press") }
        }
    }
}
```

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "off" { }
        CONTAINER STATE "bulb check" USE "bulb test" { }
        CONTAINER STATE "switch check" USE "switch test" { }
        STATE "checked" { }
    }
    TRANSITIONS {
        SPLIT "off" -> "bulb check", "switch check" {
            CONDITION { EVENT("service", "test") }
        }
        JOIN "bulb check", "switch check" -> "checked" {
            CONDITION { DONE }
        }
    }
}
```

### 2.3.12.3 Names

The states and transitions of a file refer only to the states of that file. A file never names a state inside a
fragment it uses, and a fragment never names a state of the state machine that uses it.

After flattening, a state of a fragment carries the name of its container state in front, separated by a slash. The
state `powered` of the bulb test above runs as `self test/powered`. When a fragment uses another fragment, the names
nest, and a state two levels down runs for example as `self test/wiring/powered`. The trace of a run, the debugger
and the runtime show these names.

A fragment that two container states use runs as two copies, and the copies share nothing. In the second lamp state
machine above, the bulb test runs as `bulb check/powered`. Because a flattened name must not be equal to any
other state name of the composition, a state name that contains a slash can clash with a flattened name, for example a
state `"self test/powered"` next to the container state `self test`.

Fragments are found by their names alone, and the folders and file names of the texts play no part. The fragments and
the attachable state machines of a project share one name space, and no two of them may have the same name. `ATTACH`,
`EXCHANGE` and `behaves after` name attachable state machines only, never a fragment.

### 2.3.12.4 Macros in a composition

Because the macros of all files of a composition form one set, a file may call a macro that another file of its
composition defines. A macro of a fragment that runs twice is in the set only once. Two macros of the same name with
different definitions cannot both be in the set, and such a pair is an error.

A file should define the macros it calls, since it is then easier to read and to reuse. A call of a macro that only
another file defines gives a warning at the call.

The checks of a composition are listed in [2.4.5 KStates](2.4-checks.md#245-kstates) for a single file and in
[2.4.6.5 Pages](2.4-checks.md#2465-pages) for the checks across files. What a container state, a final state and
`DONE` do at run time is described in
[3.1.14 Pages](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/reference/3.1-execution-semantics.md#3114-pages).

## 2.3.13 Compound states and container states

The compound states of [2.3.2.1 Nesting](#2321-nesting) hold inner states written in their braces. The container states
of [2.3.12 Pages](#2312-pages) run the states of a fragment as their inner states. Both group states under an
outer state whose transitions apply in each of them. They differ in where the inner states are written and in how far
the outer text can reach into them.

| | Compound state | Container state with its fragment |
|---|---|---|
| Where the inner states are written | In the braces of the state, in the same file. | In a fragment, a file of its own. Several container states may use one fragment, and each use runs a copy of it. |
| Names | One name space for the whole file. Transitions cross the border of the state freely, into and out of any inner state. | The file and the fragment each have their own name space. The using text cannot name a state of the fragment, and the fragment cannot name a state outside itself. For this reason no transition crosses the border of the container state. After flattening, a state of the fragment has the name of the container state and a slash in front ([2.3.12.3 Names](#23123-names)). |
| The `INITIAL` mark | The single mark of the file may stand on an inner state, and the state machine then starts inside the compound state. | The fragment has a mark of its own, which the using text does not see. It decides where the fragment starts. |
| What a transition into the state enters | The state itself and none of its inner states. | At once the start of the fragment, or the remembered state when the container state has a history that remembers one. A container state is never active without a state of its fragment inside it. |
| Actions | `ENTRY` and `DO` blocks. | None. The states of the fragment carry them. |
| Finishing | No final states and no `DONE`. A transition from an inner state leads out. | The fragment ends in a `FINAL STATE`. `DONE` on a transition from the container state holds once the fragment has reached one ([2.3.12.2 Container states and DONE](#23122-container-states-and-done)). |
| Leaving | A transition from the compound state leaves it from any of its inner states. | A transition from the container state leaves it from any state of the fragment and ends the fragment. |
| Histories | `SHALLOW HISTORY` and `DEEP HISTORY` remember the inner state ([2.3.7 Histories](#237-histories)). | The same, for the states of the fragment. At run time the two differ in when the remembered state is entered. [3.1.14.6 Histories, tick limits and breakpoints](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/reference/3.1-execution-semantics.md#31146-histories-tick-limits-and-breakpoints) describes the difference. |
| Tick limits and breakpoints | Allowed, as on every state. | Allowed on the container state. The states of the fragment have their own, and each copy of the fragment has its own states. |
| Macros | The macros of the file. | The macros of all files of the composition form one set ([2.3.12.4 Macros in a composition](#23124-macros-in-a-composition)). A file should call only the macros it defines itself. |

In the following example the lamp goes from full to dimmed light on a dim while it is on, and a dim in `dimmed`
switches it off. The first version uses a compound state.

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "off" { }
        STATE "on" {
            STATE "full" { }
            STATE "dimmed" { }
        }
    }
    TRANSITIONS {
        TRANSITION "off" -> "full" {
            CONDITION { EVENT("switch", "press") }
        }
        TRANSITION "full" -> "dimmed" {
            CONDITION { EVENT("switch", "dim") }
        }
        TRANSITION "dimmed" -> "off" {
            CONDITION { EVENT("switch", "dim") }
        }
        TRANSITION "on" -> "off" {
            CONDITION { EVENT("switch", "press") }
        }
    }
}
```

Written with a container state, the light levels move into a fragment.

```kstates
STATEMACHINE "fading" FRAGMENT {
    STATES {
        INITIAL STATE "full" { }
        STATE "dimmed" { }
        FINAL STATE "faded" { }
    }
    TRANSITIONS {
        TRANSITION "full" -> "dimmed" {
            CONDITION { EVENT("switch", "dim") }
        }
        TRANSITION "dimmed" -> "faded" {
            CONDITION { EVENT("switch", "dim") }
        }
    }
}
```

```kstates
STATEMACHINE ATTACHED TO "Lamp" {
    STATES {
        INITIAL STATE "off" { }
        CONTAINER STATE "on" USE "fading" { }
    }
    TRANSITIONS {
        TRANSITION "off" -> "on" {
            CONDITION { EVENT("switch", "press") }
        }
        TRANSITION "on" -> "off" {
            CONDITION { DONE }
        }
        TRANSITION "on" -> "off" {
            CONDITION { EVENT("switch", "press") }
        }
    }
}
```

With the compound state, the transition from `off` leads straight into `full`, and the transition from `dimmed` leads
straight out to `off`. The container state allows neither. The lamp enters `on`, and this starts the fragment in
`on/full`. Since the fragment cannot name `off`, it ends in its final state `faded`, and the transition with `DONE`
leads out.
[3.1.14.5 Final states and DONE](https://github.com/karpfenproject/karpfen-runtime/blob/main/docs/reference/3.1-execution-semantics.md#31145-final-states-and-done)
describes the extra step that this way out takes at run time.

A compound state suits a group of states that belongs to one state machine and needs transitions across its border. A
container state suits a piece of behaviour with a clear start and end, such as a self test, when the piece is long
enough for a file of its own or when several state machines, or several places of one state machine, run it.

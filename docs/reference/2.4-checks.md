# 2.4 Checks

The library checks texts in three steps. Each problem it finds is reported as a diagnostic with a range of the text, a
severity, a code and a message. The code names the kind of problem and stays the same across versions, while the
message may change. An error means that the text is wrong. A warning means that the text is accepted but very likely
does not do what was meant.

## 2.4.1 What is checked when

The reader of a language first parses a text and reports its syntax errors. Since the parser recovers from an error
and reads on, one text may show several syntax errors.

The reader then checks the text on its own: the KMeta reader the types, the KModel reader the objects against the
metamodel, and the KStates reader the states, transitions and macros of the state machine. Where a syntax error may
have cost the reader part of the text, the reader leaves out the checks that would report what the lost part might
hold. A text with a syntax error gets no report of an unknown state or macro in KStates, of an unknown target type or a
missing type in KMeta, or of a `knows` to a missing object in KModel.

The verifier checks these parts of the state machines of a project against the domain metamodel, the event metamodel
and the model:

- paths, operations and values
- macro calls
- events in scope
- the states that can be reached
- the names of the attachable state machines that `behaves after`, `ATTACH` and `EXCHANGE` use
- the compositions of fragments

The verifier reports a problem in the text of the state machine it concerns, and a problem of `behaves after` in the
text of the metamodel. It leaves out a state machine with a syntax error. Each of its checks runs only when the texts
it relies on have no errors.

| Checks of | Need |
|---|---|
| types | a domain metamodel without errors |
| event fields | an event metamodel without errors |
| values | a model without errors and the object the state machine runs on |
| states and events | a state machine whose state names are unique and known |

[4.4 Validating](https://github.com/karpfenproject/karpfen-IDE/blob/main/docs/reference/4.4-validating.md) describes
how the IDE shows the problems of the readers and of the verifier. [2.5 Using the library](2.5-library.md) shows how a
program calls the readers and the verifier.

| `kstates.fragment-uses-itself` | error | A container state of a fragment uses the fragment itself. Reported at the name after `USE`. | `CONTAINER STATE "again" USE "bulb test" { }` in `bulb test` |

A header without a type after `TO` is a syntax error.

The grammar allows `ATTACH` only after a rule with three operands. Since every operation other than `SETOBJ` and
`APPENDOBJ` takes one or two operands, `ATTACH` after such a rule written with its right number of operands is a
syntax error.
The same holds for a `SETOBJ` or `APPENDOBJ` written with fewer than three operands. A rule of another operation that
is written with three operands and followed by `ATTACH` parses, and it gets `kstates.action-arity` for its number of
operands, for example `SET("self", "mode", "on") ATTACH "blinking"`. In each of these cases the reader leaves the rule
out.

Since a syntax error may hide a state or a macro, the reader leaves out four checks of names and calls for a text with
a syntax error: `kstates.unknown-state`, `kstates.unknown-macro`, `kstates.macro-argument-count` and
`kstates.missing-macro-arguments`. It also leaves out the count of initial states when the `STATES` block has a syntax
error.

Because a text that is a fragment or has a container state may call a macro that another file of its composition
defines, the reader of such a text reports no `kstates.unknown-macro` and does not count the arguments of a call of a
macro that the text does not define. The verifier checks these calls against the whole composition.

A container state with a history gets no `kstates.history-without-inner-states`, since its inner states come from its
fragment. `kstates.misplaced-done` is left out while a source of the transition names no state, and
`kstates.fragment-without-final-state` is left out while the `STATES` block has a syntax error.

### 2.4.6.1 Paths

The verifier follows a path key by key, in the same way as the runtime. Each key names a relation or a property of the
type reached so far. A path goes on from the first object of a list relation, but it cannot go on from a property. In
the code of a macro, a path cannot go on from a list.

Where a path starts depends on where it stands and on its first key.

- In the code of a macro, a path whose first key is the name of a parameter starts at that parameter. Any other path
  there names a local variable of the code, which the runtime leaves to Python and the verifier does not check.
- Outside the code of a macro, a path whose first key is the name of a `WITH` block around it starts at the binding of
  the innermost such block.
- Outside the code of a macro, a path whose first key is `event` starts at the event in scope.
- Every other path starts at the object the state machine runs on.

The paths that an `IF IN SCOPE` block names are never reported, because the runtime only tests them and does not read
them. Inside the block, a path that starts with one of the paths of the block is not reported as leading nowhere. The
same holds for a path that starts with `event` when one of the paths of the block does.

### 2.4.6.2 Operations

| Rule | Needs |
|---|---|
| `SET` | A property that is not a list. |
| `APPEND`, `SETLIST`, `DROPLIST` | A list property. |
| `SETOBJ` | A relation that holds one object. |
| `APPENDOBJ` | A list relation. |
| `DROPOBJ`, `EXCHANGE` | A path to one object. |
| A `VALUE` condition | A boolean or a string property that is not a list. |

When the path of `SET`, `APPEND`, `SETLIST` or `DROPLIST` leads to a relation, the message names the relation operation
to use instead. A string target of `SETOBJ` or `APPENDOBJ` must be a path to one object of the type of the relation.
Only a `knows` relation may take such a target, since a `has` relation takes a new object.

### 2.4.6.3 Events and states

An event comes into scope at the target of the transition or split whose `EVENT` clause matched it, and it stays in
scope while that state is active. The code of a state sees the events of the transitions into the state itself, into a
state around it and into a state inside it. The conditions of a transition see the event of their own `EVENT` clause.
Without such a clause they see the events in scope in the state the transition starts in. The conditions of a join see
no event.

A state is reachable if a transition, a split, a join or a timeout leads into it, or into a state inside it, on a way
that starts at the initial state. For this check every condition counts as possibly true. A transition into a state
does not make the inner states of that state reachable, because it enters none of them.

### 2.4.6.4 Attachment

Since an attachable state machine runs on objects of each type it lists, the verifier checks the paths and operations
of such a state machine once for each type. A problem found for every type is reported once, as it is. A problem found
only for some types names the type in front of its message, for example `For type 'Dimmer': Type 'Dimmer' has no
property or relation 'lit'`.

The names that `behaves after`, `ATTACH` and `EXCHANGE` use are checked only where they are written as strings. A name
that an `EVAL` or a `MACRO` computes is checked by the runtime when the action runs. An `ATTACH` is checked against the
type of its relation. An `EXCHANGE` is checked against the type of the object its path leads to, and like `DROPOBJ` it
needs a path to one object.

A name that no attachable state machine has is not reported while a state machine of the project has a syntax error,
since that state machine might carry the name. The `behaves after` clauses are checked only in a domain metamodel
without syntax errors.

### 2.4.6.5 Pages

The verifier flattens each state machine of the project that is not a fragment together with the fragments of the
project, in the same way as the runtime does. Flattening is explained in [2.3.12 Pages](2.3-kstates.md#2312-pages). A
problem that prevents the flattening is reported in the text where it stands, also when that text is a fragment. A
problem that the reader of that text reports already, such as a fragment that uses itself, is not reported a second
time. `project.unknown-fragment` is not reported while a state machine of the project has a syntax error, since that
state machine might be the fragment.

The other checks of the project then run on the flattened state machine. There the content of a fragment is checked
where it runs, with the type of the state machine that uses it. A problem inside a fragment is reported in the text of
the fragment, once for each place in it, however often the fragment is used. A state of a fragment is reachable when
the container state that uses the fragment is reachable and the start path of the fragment and its transitions lead to
the state.

A composition that does not flatten is checked as the single state machine it starts from, as it is written. A
fragment that no state machine uses is checked on its own, as far as that is possible without the type of a state
machine that uses it. These checks cover its states and transitions, the fragments it uses and its macro calls. A
fragment that a state machine uses, but whose compositions do not flatten, is checked on its own as well. Its macro
calls are left out then, because they may rely on the macros of the state machine that uses it.

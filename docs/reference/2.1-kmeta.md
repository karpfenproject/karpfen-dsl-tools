# 2.1 KMeta

A KMeta text is a metamodel. It defines types, and each type has properties, which hold values, and relations, which
lead to objects. Metamodel files have the extension `.kmeta`. The grammar of the language is
`src/main/antlr/io/karpfen/dsl/grammar/kmeta/Kmeta.g4` in the karpfen-dsl-tools repository.

## 2.1.1 Types

A type is written as the keyword `type`, followed by its name and its description as two strings and by a body in
braces. The body holds the rules of the type in any order. Each rule is one `prop`, `has` or `knows`, and a body may
also be empty.

```kmeta
type "Switch" "A wall switch" {
}
```

The name identifies the type, and models and state machines refer to the type by its name. Names are case sensitive.
The description is text for the reader. It must be written, but it may be the empty string `""`.

A text defines one type or more. Between the description and the body a type may name the state machine that its
objects behave after, with the clause of [2.1.8 Behaviour of a type](#218-behaviour-of-a-type).

## 2.1.2 Properties

`prop("key", "type")` gives a type a property. A property holds a value of one of the primitive types `string`,
`number` and `boolean`, and the names of these types are written in lower case.

```kmeta
type "Bulb" "A light bulb" {
    prop("maxWatts", "number")
    prop("watts", "number")
    prop("lit", "boolean")
}
```

A number is a decimal number, such as `40` or `0.5`. A boolean is `true` or `false`, and a string is any text.
[2.2.3 Property values](2.2-kmodel.md#223-property-values) shows how a model writes these values.

## 2.1.3 Relations

A relation leads from an object to an object of another type or of the same type. KMeta has two kinds of relations.

`has("key", "Type")` embeds an object. The embedded object belongs to the object that holds it. A model writes it
inside its owner, and it exists only once, at that place. `knows("key", "Type")` refers to an object that is embedded
somewhere else in the model, and the model names that object by its key.

```kmeta
type "Bulb" "A light bulb" {
    prop("watts", "number")
}
type "Switch" "A wall switch" {
    prop("position", "string")
}
type "Lamp" "A lamp with a bulb, wired to a switch" {
    has("bulb", "Bulb")
    knows("control", "Switch")
}
type "Room" "The room the lamp stands in" {
    has("lamp", "Lamp")
    has("switch", "Switch")
}
```

In this metamodel the bulb is part of the lamp. The switch is part of the room, and the lamp only refers to it.

The target type of a relation must be a type of the metamodel. It may be defined before or after the type that uses
it.

## 2.1.4 Lists

Writing `list("type")` in place of the type makes a property or a relation hold a list. A list keeps the order of its
elements, and it may be empty.

```kmeta
type "Lamp" "A lamp" {
    prop("mode", "string")
}
type "Switch" "A wall switch" {
    prop("presses", list("string"))
    knows("lamps", list("Lamp"))
}
type "Room" "A room with several lamps" {
    has("lamps", list("Lamp"))
    has("switch", "Switch")
}
```

The property `presses` holds a list of strings. The relation `lamps` of the room embeds a list of lamps, and the
relation `lamps` of the switch refers to a list of lamps. A property or a relation without `list` holds at most one
value.

## 2.1.5 The root type

The readers take the last type of a text as the root type of the metamodel. In the examples of 2.1.3 and 2.1.4 it is
`Room`. Write the type of the root object of the model last. The readers themselves do not check that the root object
of a model has the root type, and a model whose root object has another type is read without a problem.

## 2.1.6 Rules of a metamodel

A metamodel must keep the following rules. The code of the problem that each broken rule gives is listed in
[2.4.3 KMeta](2.4-checks.md#243-kmeta).

- The text defines at least one type.
- No two types have the same name.
- No two rules of one type have the same key, whether they are properties, relations or both.
- A `prop` has the type `string`, `number` or `boolean`, written in lower case, or a list of one of them.
- A `has` or `knows` names a type of the metamodel, not a primitive type.
- A `behaves after` names an attachable state machine of the project that lists the type, and it stands only in the
  domain metamodel. Only the verifier of a project checks this rule, because the rule needs the state machines.

In a model every property and every relation is optional. KMeta has no default values and no inheritance between
types. The only numbers of elements it knows are one and a list.

## 2.1.7 Event definitions

The events of a project are defined in a second KMeta text, the event metamodel. Each of its types is one event. The
name of the type is the name of the event, and the properties and relations of the type are the payload that the event
carries. An event without payload is a type with an empty body.

```kmeta
// The events of the lamp example.
type "press" "Presses the wall switch" {
}
type "dim" "Turns the dimmer one step: brighter when bright is true, dimmer when it is false" {
    prop("bright", "boolean")
}
type "smash" "Breaks the lamp" {
}
```

The event metamodel names no domain. In [2.3.5 Events](2.3-kstates.md#235-events) a state machine gives the domain
together with the name of the event in a clause such as `EVENT("switch", "dim")`, and it reads the payload with paths
such as `event->bright`.

Because the event metamodel is read with the types of the domain metamodel at hand, a payload may embed or refer to a
domain type without defining it again. An event type may for example hold `has("position", "Point")` when `Point` is a
type of the domain metamodel. The event types do not become part of the domain metamodel. Like every metamodel, an
event metamodel has its last type as its root type, but for events the root type has no meaning.

## 2.1.8 Behaviour of a type

`behaves after "name"`, written between the description and the body of a type, gives every object of the type an
instance of the attachable state machine of that name. This holds for each object of the model when a run starts and
for each object that a rule of a state machine creates later. The keywords are written in lower case.

```kmeta
type "Bulb" "A light bulb" behaves after "glowing" {
    prop("watts", "number")
    prop("lit", "boolean")
}
```

The named state machine must be one of the attachable state machines of
[2.3.1 The state machine](2.3-kstates.md#231-the-state-machine), and its header must list the type, as
`STATEMACHINE "glowing" ATTACHABLE TO "Bulb"` does for bulbs. The objects of a type without the clause have no
state machine of their own unless a run or a rule attaches one. An event type cannot have the clause.

When to give a type a `behaves after` and when to attach a state machine in another way is explained in
[2.3.11 State machine management and lifecycle](2.3-kstates.md#2311-state-machine-management-and-lifecycle).
